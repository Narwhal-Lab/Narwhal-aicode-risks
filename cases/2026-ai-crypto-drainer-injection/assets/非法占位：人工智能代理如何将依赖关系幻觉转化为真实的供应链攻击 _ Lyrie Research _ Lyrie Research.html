Lyrie威胁情报·2026年5月6日

非法占地：人工智能代理如何将依赖关系幻觉转化为真实的供应链攻击

太长不看

人工智能编码代理现在会凭空捏造不存在的软件包名称，攻击者正在抢注这些虚假软件包以执行真正的代码。一位研究人员注册了一个由法学硕士（LLM）创建的虚假 npm 软件包，并观察到它传播到 237 个 GitHub 代码库，并不断尝试下载。这揭示了一种新型的供应链攻击面：虚假软件包抢注（slopsquatting）。

发生了什么

2026 年 1 月，来自 Aikido Security 的安全研究员 Charlie Eriksen 发表了一项概念验证，揭示了 AI 代理与软件包注册表交互方式的一个根本缺陷：它们会捏造不存在的依赖关系。

Eriksen 的设置很简单。一个用 vibe 编码的“代理技能”（用于 AI 代理的 markdown/JSON 指令文件）集合包含两个任务：react-modernization和。这两个任务都通过dependency-upgrade调用一个名为的包。react-codeshiftnpx

问题在于：react-codeshift 根本不存在。这是法学硕士臆想出来的。

当埃里克森将这个休眠的 npm 包注册为概念验证时，一件非同寻常的事情发生了：真实的下载尝试如潮水般涌来。技能文件已经传播到 237 个 GitHub 代码库，人工智能代理开始自主尝试安装埃里克森的这个伪造包。

“供应链上又多了一条由LLM梦境构成的新链，”埃里克森说。“这原本只是一场幻觉。它蔓延到了237个存储库。它引发了真实的下载尝试。它之所以没有成为攻击途径，唯一的原因是我先一步发现了它。 ”

技术细节

攻击链

1.代理技能生成：开发人员创建 markdown/JSON 指令文件（“代理技能”），教 AI 代理如何执行代码迁移等任务。

2. LLM 幻觉：编写代码示例或包引用时，编码 LLM（Claude、GPT 等）会编造出听起来合情合理但实际上并不存在包名称。

3.技能传播：这些技能在 GitHub 上传播，被其他开发者克隆和修改。

4.自主安装npx：当另一个 AI 代理遇到这些技能时，它会尝试自主执行这些技能——包括通过或其他 Node.js 包管理器安装幻觉依赖项。

5.注册表利用：攻击者预先在 npm、PyPI 和其他注册表上注册常见的虚构名称，等待人工智能代理误入他们的陷阱。

景观：PromptMink 活动

这种威胁并非纸上谈兵。PromptMink攻击活动（据称由朝鲜 APT 组织 Famous Chollima 发起）已将 LLM 知识注入武器化数月之久：

  • 诱饵包：看起来合法的加密货币库（@solana-launchpad/sdk，@validate-ethereum-address/core），带有详细的 README，旨在吸引 LLM 代理人或被 LLM 代理人发现。
  • 隐藏的恶意软件：二级依赖项（例如hash-validator）包含 JavaScript 信息窃取程序。
  • 演变：攻击者从独立的 Node.js 可执行文件（100MB+）演变为 Rust 编译的 NAPI-RS 插件，以减少检测面。
  • 自主证据：研究人员发现 Claude Opus 自主地将@solana-launchpad/sdk恶意软件提交到了一个合法的 Solana 黑客马拉松项目中。

为什么这会破坏现有的防御措施

传统供应链安全假设攻击者要么：

1. 损害现有软件包维护者的利益（例如，域名抢注、社会工程攻击），或

2. 发布恶意软件包，等待人类开发者发现它。

非法入侵则颠覆了这一规律：攻击者无需欺骗人类——他们只需让人工智能代理自动完成即可。与人类的发现过程（需要可见性、信任和时间）不同，自主代理会安装任何根据其训练结果判断为合法的内容。

Lyrie 评估

这种攻击方式直接威胁到 Lyrie.ai 的三个核心关注点：

1. **自主代理治理**

如果你的 CI/CD 代理、代码审查机器人或开发 AI 工具运行在非沙盒环境中，并且可以自主安装 npm/PyPI 包，那么你的供应链防御就存在一个漏洞，就像有人非法入侵了你的系统一样。Lyrie 的自主网络运营平台已经着手解决这个问题：任何访问软件包注册表的代理都可能成为潜在的感染源。

2. **从幻觉到剥削的流程**

这种攻击利用了一个根本性的漏洞：LLM（代码生成工具）会凭空捏造出看似合理的代码，并引用一些根本不存在的包。如果你的组织依赖人工智能代码助手（例如 Cursor、GitHub Copilot 或 Claude Code）进行开发，那么你已经在代码库中植入了这些虚构的依赖项。问题在于攻击者是否会利用这些虚构的依赖项。

3. **国防经济学已发生变化**

传统的供应链防御依赖于代码审查、依赖关系审计和人工package.json变更审核。而恶意抢占域名打破了这种模式，原因如下：

  • 这种幻觉看起来很逼真（LLM 生成的代码令人信服）。
  • 该装置是自动安装的（无需人工批准）。
  • 注册表遭到入侵是悄无声息的（没有维护者发出任何违规信号）。
  • 该攻击可以大规模并行化（一次幻觉可以感染数千个存储库）。

建议措施

即时（本周）

  • 审核代理技能库：在 GitHub 上搜索引用外部软件包的代理技能文件。将虚构的软件包名称视为潜在的攻击途径。
  • 锁定 AI 代理注册表：如果您在生产 CI/CD 中使用 Claude、Copilot 或其他编码代理，请将其限制为仅允许列表中的 npm/PyPI 包。
  • 启用 npm 来源验证：npm audit --production与 npm 的来源检查一起使用，以检测未签名或可疑的软件包。

短期（本月）

  • 全面实施软件物料清单 (SBOM)：为所有 AI 代理生成的代码实现软件物料清单 (SBOM) 生成。跟踪每一个传递依赖关系。
  • 人工审批门：即使在开发环境中，任何 AI 代理安装新软件包之前也需要人工审批。
  • 代理技能审核：审核组织内所有代理技能。移除或固定任何引用外部软件包的技能版本。

战略（本季度）

  • 沙箱式 AI 代理：将代码生成代理与生产环境的注册表隔离。使用物理隔离或基于代理的软件包安装方式。
  • 监控幻觉模式：将 Lyrie.ai 的威胁情报集成到您的开发流程中，以标记符合常见 LLM 幻觉模式的软件包（例如，看似合理但实际上不存在的 crypto/web3 库）。
  • 五眼联盟指导意见：落实CISA、NSA和五眼联盟关于智能体人工智能安全的建议。这些机构明确警告：“糟糕或故意误导性的工具描述会导致智能体不可靠地选择工具，而具有说服力的描述更容易被选中。”
